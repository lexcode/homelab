# Replace Nginx Proxy Manager with Traefik as the ingress stack's reverse proxy

Nginx Proxy Manager (NPM) is being retired in favor of Traefik, replacing the `nginx-proxy-manager` service in-place inside the `proxy/` (ingress) stack, alongside `cloudflared` and `tailscale-funnel`. Docker-routed backends get their routes via labels on the container itself (Traefik's Docker provider, per-stack, decentralized); external-routed backends (a handful of non-Docker LAN devices — NAS, router, an Unraid box) get a small supplementary file-provider config in the ingress stack. This was chosen over a single centralized routing file because it keeps each stack self-describing, matching this repo's existing one-stack-per-directory convention, at the cost of routing config being spread across every stack instead of one admin UI.

## Considered Options

- **Centralized file-provider config for everything** (closer to NPM's single admin UI) — rejected: means editing one shared file whenever any stack's routing changes, working against the existing per-directory stack convention.
- **HTTP-01 ACME challenge**, initially chosen to match what was assumed to be NPM's behavior, with no new secret to provision — reversed after deployment: verified via a direct DNS-over-HTTPS query (bypassing local/LAN DNS) that most `*.lexcode.dev` subdomains are DNS-only records pointing at private LAN IPs, not proxied through Cloudflare, so they're unreachable from Let's Encrypt's HTTP-01 validation servers by construction. NPM's actual working cert was a `*.lexcode.dev` wildcard obtained via DNS-01 — the assumption that NPM used HTTP-01 was wrong. Switched to DNS-01 via a Cloudflare API token (`CF_DNS_API_TOKEN`, `Zone:DNS:Edit` scope), requesting the same wildcard shape NPM actually used. See [proxy/README.md § TLS: DNS-01, not HTTP-01](../../proxy/README.md#tls-dns-01-not-http-01).
- **Migrating NPM's existing Let's Encrypt cert/account data into Traefik** — rejected: NPM's certbot-style layout doesn't map cleanly onto Traefik's `acme.json`; re-issuing fresh is cheap and avoids carrying over stale state.
- **Replicating NPM's `block_exploits` nginx snippet** (enabled on most of the migrated hosts) as a Traefik middleware — rejected as disproportionate effort for a homelab already sitting behind Cloudflare's edge filtering. Recorded here as a consciously accepted gap, not a silent one.

## Consequences

- Adding a new public route to a Docker-routed backend now means adding labels to that service's own compose file, not visiting an admin UI.
- Adding a route to a new external-routed backend means editing the ingress stack's file-provider config directly.
- The Traefik dashboard is enabled but bound internal-only — no public route, unlike NPM's `81` admin port which was itself proxied (`npm.lexcode.dev`, dropped in this migration).
- Cutover is a hard cutover (NPM stopped, Traefik started on 80/443 directly) — brief downtime while DNS-01 issues the wildcard, accepted as low-cost for a homelab.
- Renewing or extending the wildcard's coverage now depends on `CF_DNS_API_TOKEN` staying valid — if it's ever revoked or the zone changes registrar, cert renewal silently stops working until noticed (Traefik logs the ACME failure, but nothing pages anyone in this setup).
- Adding a genuinely new second-level domain (not a subdomain of the wildcard's zone) needs its own `domains` declaration and possibly its own resolver — the wildcard only covers `*.lexcode.dev` + `lexcode.dev`.
- Pin `traefik:v3.7.10`, not a floating tag — v3.3 shipped a Docker client that doesn't negotiate its API version against the daemon and hardcodes an old default (1.24), which a sufficiently new Docker Engine (here: minimum accepted API 1.40) rejects outright, silently disabling every Docker-labeled route. `DOCKER_API_VERSION` does not fix this (Traefik's client doesn't read it) — only upgrading the image does. Re-verify this class of failure before ever pinning an older Traefik tag again.
- The `traefik` service needs an explicit `dns: [1.1.1.1, 8.8.8.8]` override, same as `vpn` in `media/compose.yml` — Docker's embedded resolver (`127.0.0.11`) was unreliable enough to break DNS-01's propagation check (lego polls the container's own resolver to confirm the challenge TXT record is visible before telling Let's Encrypt to validate), even though the record was genuinely live and publicly visible via a direct external query the whole time. This is the same class of issue `media/compose.yml` already documents for `*.radarr.video`-style lookups — worth checking for on any new service added to a custom Docker network here.
- `dnschallenge.disablePropagationCheck=true` (with a fixed `delayBeforeCheck=30`) — even after the `dns:` override above, lego's own propagation check kept failing intermittently, including one transient `SERVFAIL` observed directly from Cloudflare's own authoritative nameserver for the zone, while an independent external query confirmed the record was correct and live the whole time. The local check added friction without adding safety — Let's Encrypt performs its own independent, authoritative validation regardless of what our client-side check concludes. Revisit if certs start failing for a *different* reason (e.g. genuinely stale/wrong records) now that this safety net is gone.
